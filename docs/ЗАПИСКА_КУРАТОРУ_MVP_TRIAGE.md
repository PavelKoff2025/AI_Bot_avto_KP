## 1. Что сдаю

Сдаю **развёрнутый сервис обработки обращений отдела продаж**, а не изолированный учебный endpoint.

После звонка менеджер загружает транскрибацию. Система:

1. разбирает текст;
2. сравнивает с эталоном протокола (7 обязательных полей, порог 80%);
3. либо позволяет сгенерировать КП, либо эскалирует человеку («неполные данные» + скрипт вопросов);
4. пишет аудит в SQLite (сделка, статус, журнал действий);
5. отдаёт черновик КП / письмо клиенту.

Публичная проверка: вход в CRM по ссылке выше; health: `GET http://194.67.103.144:5001/health`.

Это сознательный выход за рамки формулировки ДЗ. Учебный контракт `POST /triage` (категории billing / support / complaint / other) я **не подменяю молча** — ниже таблица расхождений и соответствие по смыслу.

## 2. Зачем вышел за букву

Формулировка ДЗ — универсальный inbox поддержки: четыре категории, черновик ответа, флаг эскалации.

Моя рабочая задача другая: **входящие отдела продаж «Дом-Мастер»** — протоколы звонков, полнота данных, коммерческое предложение. Четыре абстрактные категории здесь не про бизнес: «биллинг / жалоба / саппорт» не отвечают на вопрос менеджера «можно ли уже считать КП».

Поэтому triage в этом проекте — **разбор протокола относительно эталона**, а не сортировка тикетов в четыре корзины.

Требования практики при этом сохранены:

| Идея ДЗ | Как сделано в сдаваемом сервисе |
|--------|----------------------------------|
| Обработать обращение | Транскрибация звонка → сделка в CRM |
| Классификация | Соответствие эталону; готовность к КП / доработка |
| Уверенность | % заполнения (high ≈ ≥ 80%, иначе ниже) |
| Эскалация человеку | Статус «неполные данные», нет кнопки КП, готовые вопросы клиенту |
| Черновик ответа | Скрипт уточнений или КП тёплого контура (PDF) |
| Не выдумывать | Эталон + парсер по тексту; при дырах — эскалация, не «уверенное КП» |
| Аудит в SQLite | Таблица `deals` + `action_log` (кто что сделал) |
| Секреты в env | `OPENAI_API_KEY` и остальные ключи только в `.env` |
| Сбой LLM / сети | Шаблонное КП без AI / повтор; менеджер не видит внутренний traceback |
| Развёртывание | Путь A: публичный URL на VPS, systemd, health-check |

Стек совпадает с рекомендованным: Python 3.11, Flask, OpenAI, SQLite, Docker (образы и compose в репозитории). Дополнительно: Telegram-бот, WeasyPrint, production systemd.

## 3. Где буква задания другая — и почему

Прошу оценивать **результаты практики** (контракт, надёжность, LLM с рамками, хранение, деплой), а не совпадение имён полей 1:1.

| Буква ДЗ | Что в сдаче | Почему так |
|----------|-------------|------------|
| Ровно один endpoint `POST /triage` | Основной контур — веб-CRM + бот; HTTP есть (`/health`, сделки, генерация КП) | Один POST недостаточен для сценария менеджера ОП |
| JSON: `text`, `channel`, `client_id` | Текст протокола, канал = звонок/CRM, идентификатор = сделка / клиент | Та же входная тройка в доменных именах |
| `category`: billing / support / complaint / other | Не используются. Категория у нас — «готово к КП» / «нужна доработка» | Четыре корзины поддержки не описывают продажу дома |
| `draft_reply` 1–6 предложений | Вопросы по пробелам эталона или PDF КП | Ответ клиенту в ОП — смета, не абзац в JSON |
| `confidence`: high / medium / low | Непрерывный % эталона + порог 80% | Для приёмки полезнее измеримая полнота, чем три слова |
| `escalate`: boolean | Явная эскалация менеджеру при &lt; 80% | Тот же смысл: не уверен — человеку |
| Таблица `tickets` и поле `error` | `deals` + `action_log`; ошибки — в логах и статусах доставки | Аудит привязан к сделке, не к абстрактному тикету |
| Лимит N запросов/мин на `client_id` | Лимит тяжёлых задач на пользователя в боте; CRM за логином | Защита от спама LLM, не анонимный POST |
| Без RAG | В **учебном** `/triage` RAG нет. В CRM эталон и стандарты читаются из `knowledge_base/` | Для КП без базы стандартов нельзя честно считать цену и комплект |
| Temperature 0.2 на классификации | Для разбора протокола — структурированный JSON; креатив не нужен | Согласовано с памяткой ДЗ |

В коде остаётся учебный модуль `POST /triage` (`app/routes/triage.py`, `run_triage.py`, таблица `tickets`) — это черновик «буквы» ДЗ. **На проверку его не выставляю:** на порту 5001 работает CRM, не этот процесс. Если понадобится показать контракт 1:1, могу поднять `python run_triage.py` отдельно и прислать curl.

## 4. Как проверить сдачу (без Postman на /triage)

1. Открыть http://194.67.103.144:5001 — логин выдаёт администратор (для проверки могу выдать учебную учётку).  
2. `GET /health` → `{"status":"ok","service":"dommaster-crm"}`.  
3. Сделки: вставить протокол → % эталона → при ≥ 80% «Сгенерировать КП», иначе «Недостающие данные».  
4. Учебные тексты: `knowledge_base/demo_protocol_1.md` (≈100%) и `demo_protocol_2.md` (≈43%). На боевой CRM **не** нажимать «Загрузить демо» — это сотрёт сделки.  
5. GitHub: тег [v1.0.0](https://github.com/PavelKoff2025/OfferDesk/releases/tag/v1.0.0), changelog в корне.

## 5. Просьба к приёмке

Прошу засчитать работу как **MVP обработки обращений**, выполненный на реальном процессе ОП, с публичным развёртыванием.

Расхождения с чеклистом (`/triage`, четыре категории, таблица `tickets`) — не недоделка, а замена учебного inbox на предметный triage звонка. Критерии практики (валидация входа, рамки промпта, эскалация при сомнении, аудит, секреты в env, доступная проверка) в сдаваемом сервисе есть.

Готов ответить на вопросы и при необходимости отдельно показать учебный `POST /triage`.
